## Requirement changes

| ID | Original (P3) | Revised (P4) | Why it changed |
|---|---|---|---|
| R1 | When a command matches several rules, the program asks for clarification, and modifies the file with new rules. | Reordering rules that do not compete for a command never changes its outcome. When two rules do compete, the later one wins. | Feasibility and conflict. An interactive clarification prompt that rewrites the config would need a new TUI flow, and it contradicts the documented "last matching rule wins" semantics that every example config in the permissions docs relies on, such as `{"*": "ask", "rm *": "deny"}`. The three interviewees also disagreed on the resolution rule (error, most specific wins, any allow wins). What they agreed on was that order should not cause surprises. The revision keeps that: order only matters between rules that genuinely overlap, which is the documented behavior, and the property makes it explicit. |
| R3 | Acceptance criterion: the user must type and enter "yes" to a dedicated confirmation prompt. | Acceptance criterion: the command goes through the existing permission "ask" prompt instead of being allowed. | Feasibility. A separate typed-confirmation prompt would duplicate the ask flow that already exists for every tool call. The requirement text is unchanged; the acceptance criterion now uses the existing override mechanism, which is what S-3 asked for ("users should be able to override"). |

R2, R4, and R5 are kept as written. R2 was not buildable without new state, so the state was added rather than the requirement weakened: the permission service now remembers rules that denied a command in the running instance and publishes a `permission.unblocked` event when the same command is later not denied; the TUI shows it as a notification. R4 is kept as written; opencode already implements it through the `external_directory` permission, and the property checks that boundary against an independent prefix oracle.
