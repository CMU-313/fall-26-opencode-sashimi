# Traceability: Inseo Kim (inseok)

**Target feature:** Tool permission request descriptions and approval dock for read/write/edit requests in the agent permission flow (main source files: `packages/tui/src/routes/session/permission.tsx`, `packages/opencode/src/cli/cmd/run/permission.shared.ts`, `packages/opencode/src/cli/cmd/run/tool.ts`, `packages/opencode/src/tool/write.ts`).

## Requirements

| ID | Interview evidence | Requirement | Acceptance Criteria | Changed in P4? | Property (kind) | Test |
|---|---|---|---|---|---|---|
| R2 | C-22: “read, write, edit”; S-3: “recognize a read request as distinct from an edit request”; O-12 | The description must state the action type (read, write, or edit) in plain words and must match the permission being requested. | A read request for src/components/Button.tsx displays “Agent wants to read the file src/components/Button.tsx”. A write request for the same path displays a description containing “write” and not “read”. | no | Model / oracle | `permission.shared.test.ts`: For generated read, write, and edit requests and paths, compare displayed action wording with the requested action; `write.test.ts` checks emitted write metadata. |
| R3 | C-3: “mentioning the file name”; C-18; S-7; O-10 | The description must name the specific file the tool call is requesting. | A request for Button.tsx displays a description containing Button.tsx. A subsequent request for Link.tsx displays a description containing Link.tsx and not Button.tsx. | no | Invariant | `permission.shared.test.ts`: For generated file paths, assert the description contains the requested filename and does not contain a different generated filename. |
| R4 | S-4; S-7: “only the file name should change in the description”; O-4; O-5 | When only the requested file changes, the rest of the description and the control options (Allow once, Allow always, Reject) must remain identical. | Two read requests that differ only in file path produce descriptions that are identical once the path text is removed, and the dock shows the same three controls in the same order for both. | no | Metamorphic | `permission.shared.test.ts`: Replace a generated read-request path with another path; after removing the path, assert the description is unchanged and the controls remain Allow once, Allow always, Reject in the same order. |
| R5 | C-19: “a little unnecessary details”; C-20 | A write description must summarize the content by size (line count or character count) and must not display the content or narrate individual line changes. | A write of a 42-line file to notes.txt displays a description that names notes.txt and states 42 lines. The description contains none of the written text. | no | Invariant | `permission.shared.test.ts`: For generated file contents, assert the write description names the file, reports the correct line count, and includes neither the content nor individual line changes; `write.test.ts` checks emitted line-count metadata. |
| R6 | S-10; O-12; O-13 | A write-permission explanation must clearly identify whether the operation will create a new file or modify an existing file, and name the target. | A write request for a new target displays “Write new file” and its path. A write request for an existing target displays “Write existing file” and its path. | yes | Metamorphic | `permission.shared.test.ts`: For generated target paths, compare write requests with `exists` false and true; assert the explanation distinguishes new from existing, names the same target, and leaves the approval controls unchanged; `write.test.ts` checks emitted existence metadata. |

Properties written or suggested by opencode or another AI tool: R2, R3, R4, R5, R6.  Each one was verified by me against the requirements and acceptance criteria.

## Requirement changes

| ID | Original requirement (P3) | Revised requirement | Why it changed |
|---|---|---|---|
| R6 | A tool call that requires permission must remain paused while the description is displayed and must execute only after the user selects Allow once or Always allow. | A write-permission explanation must clearly identify whether the operation will create a new file or modify an existing file, and name the target. | The original requirement is outside the scope of the feature, which is explaining tool actions before approval, thus it is not feasibile to implement the properties for this requirement. The revised requirement reflects interview evidence about distinguishing file creation from editing, and is within the feature's scope. |

R2-R5 are kept as written because they are in scope and have checkable acceptance criteria. R6 required an addition to the tool test confirming that write requests include the file-existence and line-count metadata the descriptions use. The CLI formatter and TUI display were updated to show those descriptions and avoid displaying write diffs.
